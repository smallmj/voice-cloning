# 0017 — 索引层改用 SQLite，音频仍是文件

日期：2026-09-18 · 状态：已采纳 · 关联：ADR-0003、ADR-0012、plan §2 #6

## 背景

`plan.md` §2 决策 #6 一开始就写的是「全本地存储：**SQLite** + 音频目录 + 系统钥匙串」，§3 架构图也写着「SQLite + 音频文件 + 音色元数据」——但代码里 `sqlite` 一次都没出现。实际是 **5 个手写 JSON 索引**（`voices.json` / `generations.json` / `compare.json` / `regression.json` / `settings.json`）加 `app_state.json`，而 12 条 ADR 里没有一条记录过这次变更。

审计显示这不是无害偏差，而是**一整类缺陷共同的根因**：

- 每个 store 各写一遍 `__init__`/`_load`/`reload`/`_save` + `threading.Lock` 与增删改查（约 120 行可消除的重复），且第 4 份已经开始分叉；
- `persist()` 每次都**全量排序重写整个文件** → 一个 200 段的任务约 **400 次全量重写**，耗时随历史规模呈平方增长；
- 记录按**引用**存入 store，而生成日志在 executor 线程**无锁 append** → `GET /generations` 与 `_save()` 可能序列化到正在被追加的列表（落盘日志被截断），而代码注释断言"无并发修改"；
- 写临时文件**没有 fsync**，且 `_load` 把不可解析的 JSON 当作空库 → **静默丢库**，连 `.tmp` 都没有可恢复的；
- 搜索与分页是**锁内全量线性扫描**，每次击键都跑一遍。

## 决策

1. **索引层改用 SQLite**，用 Python 标准库 `sqlite3`——**不新增依赖**（sidecar 的惯例是无重依赖）。音色、生成、对比、回归、设置、应用状态各一张表。
2. **音频与参考样本仍然是文件**，不放进数据库。体积与"整库可整体拷贝"的直觉都要求如此。
3. **单个数据库文件放在数据根目录**，与现有 JSON 索引同级。
4. **备份与整库拷贝必须用一致性快照。** 启用 WAL 后直接拷贝数据目录会拿到不一致状态，因此整库备份走 `VACUUM INTO` 生成单文件快照再打包。这是对 ADR-0012「备份/恢复的搬运单位是数据根目录」的**收紧**，ADR-0012 需加一条修正指针。
5. **一次性迁移，且迁移前必须自动备份。** 启动时若发现 JSON 索引而数据库为空，则先把原 JSON 备份到数据根目录下的迁移目录，再导入并写入迁移标记；**迁移失败不得删除原文件**。
6. 测试使用临时目录或内存数据库，不引入外部服务。

## 后果

- `plan.md` §3 架构图的「SQLite + 音频文件 + 音色元数据」由待实现变为事实；§2 #6 的警示标记去掉。
- 一并消失的东西：4 份 store 的样板与分叉、全量重写、引用别名（查询改为返回新对象）、"解析失败当空库"这类静默失败（SQLite 损坏会明确报错）、以及击键级的全量线性扫描。
- 新增的成本：迁移与回滚预案；以及**"整库就是几个可读文件"的可检查性被削弱**——用诊断页的导出能力与 `sqlite3` CLI 补偿。
- 备份路径的行为发生变化：从"压缩数据目录"变成"先快照再压缩"。恢复路径需要能识别并接受快照格式。

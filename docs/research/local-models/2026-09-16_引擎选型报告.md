# 第一部分 · Apple Silicon（MPS / Metal）支持现状

## 1.0 五条可行技术路线的本质区别

| 路线 | 运行时 | 跨平台性 | 适合桌面应用？ | 代表实现 |
|---|---|---|---|---|
| **PyTorch MPS** | `torch.backends.mps` | 同一份 Python 代码在 Win(CUDA)/Mac(MPS) 都能跑 | ⚠️ 能跑，但大模型常落到 <0.5× RTF；算子缺失与内存泄漏要自己扛 | 各模型官方仓库 |
| **MLX** | Apple `ml-explore/mlx` | **仅 Apple Silicon**（无 Linux/Windows 轮子） | ✅ Mac 上最快的通用选择 | `mlx-audio`、`mlx-speech`、`f5-tts-mlx`、`soniqo/speech-swift` |
| **CoreML / ANE** | `coremltools` + Neural Engine | 仅 Apple | ✅ 最省电、最稳，适合小模型（Kokoro/Supertonic） | `aufklarer/*-CoreML`、`mattmireles/kokoro-coreml` |
| **ONNX Runtime（CoreML EP / CPU EP）** | `onnxruntime` | **Win/Mac/Linux 全覆盖** | ✅✅ 打包桌面应用的最优解 | `kokoro-onnx`、`piper`、`index-tts-2.5-onnx`、`soniqo/speech-core`（C++17）、`sherpa-onnx` |
| **llama.cpp / GGUF** | `llama.cpp` + Metal/BLAS | Win/Mac/Linux 全覆盖 | ✅ 适合 LLM-backbone 类 TTS（Orpheus、NeuTTS、OuteTTS） | `orpheus-cpp`、`neutts` GGUF、OuteTTS GGUF |

> **关键工程判断**：ONNX Runtime 的 **CoreML Execution Provider** 官方文档明确要求 "iOS 13+ / macOS 10.15+"，且 **macOS 官方 Python wheel 自带 CoreML EP**（[onnxruntime CoreML EP 文档](https://onnxruntime.ai/docs/execution-providers/CoreML-ExecutionProvider.html)）。但要注意一方实测结论：**动态 shape 会杀死 ANE 性能** —— Kokoro 这类 transformer 的 token 序列长度每次不同，"每个新 shape 都会触发 CoreML 图重编译"，因此固定 shape 的 CNN 类模型（vocoder）才适合上 CoreML，主干网络更适合 MLX/GPU（[Xybrid: ONNX Runtime 6.8x faster on Apple Silicon with CoreML](https://www.xybrid.ai/blog/onnx-runtime-6x-faster-apple-silicon-coreml)）。

## 1.1 最重要发现：`soniqo/speech-swift` + `soniqo/speech-core`（原生 Apple 全栈）

**这是一个已经开源、Apache-2.0、并且已经公开逐模型实测数据的 Apple Silicon 原生语音栈**，非常适合"打包 macOS 桌面应用"这个目标。

- **`soniqo/speech-swift`** — Apache-2.0，Swift + MLX + CoreML，Mac/iOS，Homebrew 可直接安装（formula `speech`），Swift Package Manager 可嵌入。号称有 **16 个可验证引用了该 package 的公开仓库**（含 AnythingLLM、Palmier Pro、Jabber 等）。
- **`soniqo/speech-core`** — Apache-2.0，**C++17**，面向 **Linux / Windows / Android**，ONNX Runtime + LiteRT 双后端，自带 **OpenAI 兼容的 `POST /v1/audio/speech`** 本地服务，并有 Windows 自包含 x64 ZIP 发行包。
- 两者是"Apple 兄弟 / 非 Apple 兄弟"关系：**同一个团队、同一套模型目录，Mac 走 MLX+CoreML，Win/Linux/Android 走 ONNX/LiteRT。这正好就是一个双平台桌面应用需要的架构。**
- 模型权重发布于 HuggingFace 组织 [`aufklarer`](https://huggingface.co/aufklarer)（Apple/MLX 侧）与 [`soniqo`](https://huggingface.co/soniqo)（ONNX/LiteRT 侧）。

### 1.1.3 IndexTTS-2.5 的三条独立打包路线（2025-2026 新增，非常重要）

同一作者（yunfengwang）发布了**三个 torch-free 的 IndexTTS-2.5 推理包**，全部自动从 HuggingFace 下载权重，全部是 `uvx` 一键运行：

| 包 | 后端 | 平台 | 关键实测（原文） | 许可 |
|---|---|---|---|---|
| [`index-tts-2.5-mlx`](https://pypi.org/project/index-tts-2.5-mlx/) v0.1.1 | **MLX**（int8 GPT） | Apple Silicon M1+ / macOS 13+ / Py3.10+ | **"RTF ≈ 0.45，比官方 PyTorch MPS 后端快约 2.4×"**，完全跑在统一内存 GPU 上 | Bilibili-IndexTTS |
| [`index-tts-2.5-onnx`](https://pypi.org/project/index-tts-2.5-onnx/) v0.1.0 | **ONNX Runtime** | Linux/Win/macOS，x86/ARM，CPU **或 CUDA**，且 **`--device` 支持 `coreml`** | fp32 与 PyTorch CPU 参考**逐 token 位精确**（73/73、83/83），各阶段 cosine ≥ 0.9999 | Bilibili-IndexTTS |
| [`index-tts-2.5-mnn`](https://pypi.org/project/index-tts-2.5-mnn/) v0.1.1 | **MNN**（阿里 CPU 推理引擎） | 任意有 Python 3.10+ 的系统（CPU-only） | **Apple M5 Pro / 4 线程 / ~3 s 音频**：MNN fp32 合成 9.20 s **RTF 3.16**；MNN fp16 9.48 s **RTF 3.25**；ONNX Runtime fp32 CPU 9.53 s **RTF 3.27**。MNN 声码器比 ORT CPU 快约 4×（1.12 s vs 4.81 s） | Bilibili-IndexTTS |

**这三者的实践含义**：
- Mac 上用 `index-tts-2.5-mlx`（RTF 0.45，比 PyTorch MPS 快 2.4 倍）→ 印证了 **PyTorch MPS 下 IndexTTS-2 的 RTF ≈ 1.0–1.1**（与 Soniqo 的 1.0、tts-bench 的 0.1× 口径不同，见下）。
- Windows 上用 `index-tts-2.5-onnx` + `onnxruntime-gpu`（CUDA 快路径）或走 CoreML/CPU。
- 这是**目前已验证的、IndexTTS 系列唯一可"打包分发"的非 PyTorch 路线**。
- ⚠️ **许可证**：三个包都标 `Bilibili-IndexTTS`，即继承 bilibili 模型许可，**不是 Apache-2.0**。

> **RTF 口径冲突提醒**：Soniqo 说 IndexTTS2 clone 在 M5 Pro 上 RTF=1.0（MLX fp16）；tts-bench 说在 M4 16GB 上 **0.1×**（≈RTF 10）；`index-tts-2.5-mlx` 说 MLX RTF≈0.45 而 PyTorch MPS ≈1.08。三者硬件、量化、模型版本（2 vs 2.5）都不同，**必须并列引用，不能取其一**。

## 1.3 MPS 的已知故障类（技术层面 + 一手证据）

### 1.3.1 三类可复现的 MPS 故障

**(a) `float64` 完全不支持**
> `TypeError: Cannot convert a MPS Tensor to float64 dtype as the MPS framework doesn't support float64. Please use float32 instead.`
> —— [ChatTTS-ui issue #143](https://github.com/jianchang512/ChatTTS-ui/issues/143)（2024-06-20）
> 同一 issue 中用户升级后反馈：**"拉取最新的，不报错了。但是推理时长异常的长，并且生成的音频是异常的"** —— 即**修好了崩溃、但输出音频是坏的**。

**(b) 算子未实现（`aten::*` not implemented）**
- `The operator 'aten::unfold_backward' is not currently implemented for the MPS device` —— [F5-TTS issue #443](https://github.com/SWivid/F5-TTS/issues/443)（2024-11-10，macOS 14.4.1 / torch 2.4.1）。**推理与训练 UI 同时报错。** 该 issue 至今（2025-03）仍无解决，maintainer 在 [#875](https://github.com/SWivid/F5-TTS/issues/875)（2025-03-18）里给出的方案是转向第三方 MLX 端口。
- `NotImplementedError: Output channels > 65536 not supported at the MPS device.` —— [Spark-TTS issue #12](https://github.com/SparkAudio/Spark-TTS/issues/12)（2025-03-02）。用户的 workaround 是**把 `cuda:{device}` 直接改回 `cpu`**，即 Spark-TTS 在 Mac 上**实际只能 CPU**。

**(c) MPS 统一内存水位误判 → 假 OOM（最容易踩且最难查的一类）**
- OmniVoice 在 16GB M4 上，长提示词报 `MPS backend out of memory (MPS allocated: 3.38 GiB, other allocations: 16.73 GiB)`，**但实际占用只有约 1.1 GB**。
- **修法**：`omnivoice_runner.py` 在 import torch 前设置 `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.0`（关闭提前 OOM 上限）。修完后默认音色长文本可跑到 **~0.4–0.7× RTFx**；克隆路径 mps 通过 **4/5** 提示词，只有 30 词长文本真的越过 16GB 被 OS 杀掉（SIGKILL），cpu 则 5/5 全过。
- 来源：tts-bench `docs/known-issues.md`

### 1.3.2 MPS 的"沉默陷阱"：静默回落 CPU（比崩溃更危险）

一个已经出货的桌面应用（VoiceStudio）在其工程 spec 里把这个坑写得很清楚：

> `get_best_device()` … returns the best available device, and engines just `.to(device)`. **A CUDA-only engine on a Mac, or any engine on a driver-broken / arch-mismatched NVIDIA box, silently runs on CPU (~10× slower) with no signal in Settings or at synth.**
> —— [VoiceStudio docs/specs/longform/21-gpu-compat-matrix.md](https://github.com/debpalash/VoiceStudio/blob/main/docs/specs/longform/21-gpu-compat-matrix.md)

该文档还明确指出 **MPS 上的"显存"只能按 `psutil.virtual_memory().total / 2` 估算**（统一内存没有独立 VRAM 可查），因此无法做真实的显存预检 —— **任何基于 VRAM 的自动降级/限流策略在 Mac 上都是估算**。

### 1.4.3 Mac 上的中文用户实践（来自中文社区调研）

- **DeepSpeed 完全不支持 macOS / Apple Silicon / CPU-only**（官方明确 "❌ 不支持 macOS ❌ 不支持 Apple Silicon ❌ 不支持 CPU-only ❌ 需要 CUDA toolchain"）。IndexTTS2 在 Mac 上必须用 `uv sync --extra webui`（**不要** `--all-extras`），启动加 `--fp16 --no-deepspeed --no-cuda-kernel`，Python 调用须 `use_deepspeed=False, use_fp16=True`。
  来源：[IndexTTS2 入门指南：从模型概念到 macOS 安装实战](https://jishuzhan.net/article/2041318523595718658)（2026-04-07）
- **V2EX 实测**：用户 yulon（2025-08-29）"我是 **Mac mini 4** 当副机，跑 **GPT-SoVITS**，也就 **3G 显存**左右"。
- 中文社区 Mac 场景被点名最多的组合：**GPT-SoVITS（约 3GB）与 CosyVoice / VoxCPM**；IndexTTS 在 Mac 上"能跑但慢"。
- 详细社区证据见工作区文件 `research/2026-09-16_中文TTS社区共识调研.md` §4.3。

## 1.5 结论：Mac 上"真正可靠的非 PyTorch 路线"清单

**按"可打包脆弱度"从低到高排列：**

| 优先级 | 方案 | 具体实现 | 证据 |
|---|---|---|---|
| ★★★ | **ONNX Runtime（CPU EP）** | `kokoro-onnx`、`OHF-Voice/piper1-gpl`（`pip install piper-tts`，附 C/C++ `libpiper`）、`index-tts-2.5-onnx`、`soniqo/speech-core`（C++17，含 Windows ZIP） | ✅ 成熟且跨平台 |
| ★★★ | **llama.cpp / GGUF + Metal** | `neuphonic/neutts-air-q4-gguf` 等（官方给 macOS Metal/BLAS 编译参数）、`orpheus-cpp`（官方给 `whl/metal` 索引）、OuteTTS GGUF | ✅ |
| ★★★ | **CoreML / ANE** | `aufklarer/Kokoro-82M-CoreML`、`aufklarer/Chatterbox-Flash-CoreML`、`aufklarer/Supertonic-3-CoreML`、`aufklarer/Magpie-TTS-Multilingual-357M-CoreML-8bit`、`mattmireles/kokoro-coreml`；注意 **动态 shape 会杀死 ANE 性能** | ✅ 但只适合固定 shape 小模型 |
| ★★★ | **MLX** | `Blaizzy/mlx-audio`（MIT，Swift 包可嵌入）、`appautomaton/mlx-speech`（MIT）、**`soniqo/speech-swift`（Apache-2.0）**、`lucasnewman/f5-tts-mlx` | ✅ 覆盖面最广 |
| ★★ | **MNN（CPU，torch-free）** | `index-tts-2.5-mnn`（阿里 MNN，跨全平台，声码器比 ORT CPU 快 4×） | ✅ 但只有 IndexTTS |
| ★ | **PyTorch MPS** | 各模型官方仓库 | ⚠️ 算子缺失 + 内存泄漏 + 静默回落 CPU |

**明确不建议在 Mac 上使用**（有 NC 许可之外的工程理由）：GPT-SoVITS（官方劝退 MPS）、ChatTTS、Spark-TTS、MegaTTS3、Dia、Zonos2、MARS5、LuxTTS、StyleTTS2（wrapper 硬编码 CPU）、以及一切在 tts-bench 里被标 `gpu-class` 的大模型。

### 2.8.3 中文"多音字 / 数字+英文混读"的实证缺陷

- **index-tts Issue #126**（2025-04-26）《数字和字母结合的朗读问题》原文：
  > "如果数字在前，比如 **"2H"，完全可以正确的读出来。但如果数字在后，比如 "H2"，后面的数字就无法识别了。**"
  > normalized text: `我发现啊 ,二h的铅笔似乎比h2十三的铅笔更硬.`
- **IndexTTS 官方 README 拼音说明**（原文）：
  > "拼音控制并不是对所有声母韵母（辅音、元音）组合都生效，**系统仅保留中文合法拼音的发音**"（详见 `checkpoints/pinyin.vocab`）
- **CosyVoice 3 官方卖点**（README 原文）：`Pronunciation Inpainting` 支持中文拼音与英文 CMU 音素；`Text Normalization` 支持数字、特殊符号与各类文本格式，**无需传统前端模块**。→ **中文数字/英文混读维度，CosyVoice3 更工程化**。
- **ChatTTS 已知缺陷**（社区飞书文档）："**对于阿拉伯数字，标点符号**，refine 后效果不太好"；"**自动删除或者增加一些内容**在句子里，比如输入'你吃饭了没'，会莫名改写成了'好吃，你吃饭了没'"；"即使同一个 audio seed，如果使用不同的语句分段方式…生成的音色也不是很稳定"。

### 2.10.1 一个"集群性"故障：MPS 的 `>65536` 通道上限

同一个 PyTorch 限制 `NotImplementedError: Output channels > 65536 not supported at the MPS device.` **已在至少两个模型上确认**：

- **IndexTTS-2** — [issue #193](https://github.com/index-tts/index-tts/issues/193)（2025-06，Apple M3 Max，`PhysMem: 97G used`）原文：
  ```
  >> start inference...
  NotImplementedError: Output channels > 65536 not supported at the MPS device.
  As a temporary fix, you can set the environment variable `PYTORCH_ENABLE_MPS_FALLBACK=1`...
  ```
  作者自述绕行：**"add option `--device cpu` to indextts will make it work, but very slow"**。
  ⚠️ **版本相关且不一致**：一人称 `torch==2.7.0` 修好了他的 M4，另一人回"M1 Max，torch 2.7.0 仍然有这个问题"；维护者让升 macOS 15.1+，但报告者已在 15.5 仍失败。
  官方 CLI 的 MPS 支持 PR [#78](https://github.com/index-tts/index-tts/pull/78)「Add a new Command-Line Interface and support for mps device (Apple Silicon)」**已 merged**（2025-04-11）。
- **Spark-TTS** — [issue #12](https://github.com/SparkAudio/Spark-TTS/issues/12)（2025-03-02）原文与 IndexTTS 同错；更硬的是它的崩法是 **SIGABRT 而非可捕获异常**：
  ```
  .../MetalPerformanceShadersGraph/Core/Files/MPSGraphExecutable.mm:3561:
  failed assertion `Error: MLIR pass manager failed'
  infer.sh: line 45: 16457 Abort trap: 6
  ```
  [issue #95](https://github.com/SparkAudio/Spark-TTS/issues/95)（open）确认 **`PYTORCH_ENABLE_MPS_FALLBACK=1` 也不解决**；"升级到 macOS 15.1+ 就好"的说法被证伪（回复："macOS 15.3.1, not work"）。

### 2.10.3 CosyVoice：一条被低估的 CoreML 路线

**`FluidInference/FluidAudio`（Swift）+ HF `FluidInference/CosyVoice3-0.5B-coreml`（标注 Apache-2.0）** —— 四阶段分派 CPU + ANE + GPU。其文档给出一条**必须知道**的告警原文：

> `Flow-N250-fp16 | CPU + GPU | … (pure CPU overflows fused LayerNorm → **NaN**; ANE refuses to compile; GPU path uses fp32 accumulators internally and is stable)`

→ 即 **CosyVoice3 的 Flow 阶段在纯 CPU 上会产生 NaN，在 ANE 上编译失败，只有 GPU 路径稳定**。打包时必须按此分派，不能"统一走 CPU"。

维护者对 MPS 的官方态度（[issue #134](https://github.com/FunAudioLLM/CosyVoice/issues/134)，2024-07-14 建，**至今 open**）原文：
> **"There used to be PR using MPS, but it is slower than cpu on mac, maybe it is not mature yet"**

MPS PR 史：**#1129「Add limited support for MPS devices」closed**；**#1869「add Apple Silicon (MPS) support for macOS ARM64」open**（+220 −35，merge commit `1cb52d5b`）；Issue #1767「mac gpu支持」**因 stale 自动关闭**。附带报错：`Sliding Window Attention is enabled but not implemented for 'sdpa'; unexpected results may be encountered.`

**soniqo CosyVoice3 在 M2 Max + MLX 上 RTF ≈ 0.5**（快于实时）。

### 2.10.4 GPT-SoVITS：「名义支持 MPS，实际不生效」的教科书案例

- **官方 README 原文（加粗警告）**：
  > **"The models trained with GPUs on Macs result in significantly lower quality compared to those trained on other devices, so we are temporarily using CPUs instead."**
- **README 正文直接给数**：`0.028 tested in 4060Ti, 0.014 tested in 4090 (1400words~=4min, inference time is 3.36s), **0.526 in M4 CPU**`
- **PR [#183](https://github.com/RVC-Boss/GPT-SoVITS/pull/183)「Add MPS Backend Support for macOS」merged**（2024-01-24），但 [issue #2612](https://github.com/RVC-Boss/GPT-SoVITS/issues/2612)（**open**，2025-09-21）原文：
  > "I've used mps parameter when I run install.sh, but the log shows the device still is CPU but not mps, then I read the install.sh, find that **the treatment for mps and cpu is same!** … only 111.21it/s, **My GPU is Apple M4 Max with 40CU**, So it must runs on cpu"
- 另有用户直击维护者："**别用 MPS，太慢，内存漏麻了**"（[issue #808](https://github.com/RVC-Boss/GPT-SoVITS/issues/808)）；"目前综合效果和速度，**cpu > mps**"。
- **非 PyTorch macOS 路线：未核实**（无官方/主流 ONNX/CoreML/MLX 移植；社区仅有 CPU 优化 fork `baicai-1145/GPT-SoVITS-CPUFast`）。

### 2.10.5 Kokoro：本批次 Apple Silicon 体验最好的模型（四条后端全通）

**四条可用后端**：PyTorch MPS（README 有专门的 "MacOS Apple Silicon GPU Acceleration" 段落，需 `PYTORCH_ENABLE_MPS_FALLBACK=1`）/ ONNX Runtime（含 CoreML EP）/ **原生 CoreML + ANE** / MLX。

**最完整的一组 ANE 实测**（`mattmireles/kokoro-coreml`，测量时间 **2026-06**）：

| 音频时长 | M2 Studio (64GB) | M2 Air (24GB) | M1 Mini (16GB) |
|---|---:|---:|---:|
| 3 s | **51 ms** | 148 ms | 236 ms |
| 10 s | **126 ms** | 466 ms | 712 ms |
| 30 s | **379 ms** | 1,405 ms | 1,958 ms |

原文：**"That's 12-79x realtime across the lineup"** / **"30 seconds of speech in 379 ms on a Mac Studio. 2x faster than MLX on the same hardware. Running on the Apple Neural Engine."**
同机同句同 voice（`af_heart`）vs MLX（`Blaizzy/mlx-audio` 0.4.3 + `mlx-community/Kokoro-82M-bf16`）：30 s **379 vs 763 ms**（M2 Studio，**2.0×**）/ 1405 vs 2600（M2 Air，1.9×）/ 1958 vs 3078（M1 Mini，1.6×）。
该模型卡原文：**"Apache 2.0, inherited from Kokoro-82M. Ship it. Sell it. Fork it."**

**ONNX/CPU 侧**：`thewh1teagle/kokoro-onnx` README 原文 "**Fast performance near real-time on macOS M1**"、"~300MB (quantized: ~80MB)"。
`sherpa-onnx` 侧（[PR #1713](https://github.com/k2-fsa/sherpa-onnx/pull/1713)，2025-01-15 merged）维护者原文：
> "Even though kokoro TTS claims it has only about 82M parameters, it is by far the **LARGEST** model we have in sherpa-onnx. It is also the **SLOWEST TTS model on CPU** in sherpa-onnx"
实测 `Elapsed seconds: 12.287 / Audio duration: 14.250 / **RTF: 0.862**`（单线程 MacBook Pro）。
⚠️ **但注意 tts-bench 的对照结论**：Kokoro 走 **PyTorch MPS 比走 MLX 快**（mps 13.8× vs MLX 慢 0-6%），**并且 mlx-audio 上有已知崩溃**。→ **Kokoro 在 Mac 上应选 CoreML 或 MPS，而不是 MLX。**

**许可**：代码 + 权重 **都是 Apache-2.0**，且音素化三层管线 "all Apache-2.0 licensed, **no GPL dependencies**"（soniqo 原文）。**这是本报告中最干净的"可商用 + Mac 原生快"组合。**

### 2.10.6 Piper：许可比想象的复杂得多

- **代码是 GPL-3.0**（`COPYING` 原文 `GNU GENERAL PUBLIC LICENSE Version 3`；PyPI `piper-tts` v1.6.0 元数据 `License: GPL-3.0-or-later`）。**tts-bench 的 known-issues 把 Piper 列在 MIT 里是错的。**
- **音色（voice）逐个不同许可 —— 必须逐条查**（已逐一 curl HF `MODEL_CARD`，2026-09-16）：

| Piper 音色 | 权重许可 |
|---|---|
| `en_US/ryan/high` | **CC BY-NC-SA 4.0**（非商用！） |
| `en_GB/alba/medium` | **CC BY 4.0** |
| `en_US/amy/medium` | `License: See URL`（未明示） |
| `en_US/lessac/medium` | Blizzard 2013 许可 |

→ **"Piper 是 MIT 所以随便用"是错的**：应用是 GPL-3.0，音色许可还要逐个核。
- **技术上对 Apple Silicon 最友好**：纯 ONNX Runtime，**根本不用 MPS**；官方 BUILDING 文档说明用 Python stable ABI，"Piper wheels only need to be built once for each platform (**Linux, Mac, Windows**)" → **有 macOS wheel**。仓库 README 另有 "**Looking for Maintainers**" 提示（OHF 正在找维护者）。
- **M 系列实测 RTF：官方未给 → 未核实**（tts-bench 的 M4 33.5× 是第三方实测）。

## 2.11 补充（第二批并行调研）：另外 18 个项目的 Apple Silicon 一手结论

> 来源：`apple-silicon-tts-report.md`（工作区根目录，2026-09-16 完成，全部结论来自一手来源）。**本节修正/补充了 §1.4 中若干模型的状态，并新增了一条重要的一手许可证纠错。**

### 2.11.1 【结构性结论】这一批模型在 MPS 上失败的三大根因

**对于本批 18 个项目，可靠路线是 MLX（mlx-audio / mlx-community），不是 PyTorch MPS。** MPS 在 Dia、Zonos、OpenVoice、Chatterbox、Qwen3-TTS、MOSS-TTSD、VibeVoice 上都是坏的或严重退化。故障可归为三类：

| 根因 | 具体报错 | 命中模型 |
|---|---|---|
| **GQA + `scaled_dot_product_attention` 在 MPS 上** | `loc("mps_matmul"...): error: incompatible dimensions` / `invalid shape` → **`LLVM ERROR: Failed to infer result type(s)`** | **Dia**（#136/#197）、**Zonos**（#44） |
| **`torch.compile`/Triton 与 flash-attn 没有 MPS 构建** | 编译失败 / 导入即错 | **Kimi-Audio**（#15）、**Qwen3-TTS**（#69）、**MOSS-TTSD**（#22）、**Step-Audio**（README 要求 CUDA） |
| **`torch.load` 未带 `map_location`** | 在 MPS-only 机器上硬失败 | **Chatterbox**（#85、#357） |

# 第三部分 · 落地建议

## 3.1 推荐的架构（双平台，同一份模型资产 / 两套运行时）

```
                      ┌─────────────────────────────────────────────┐
                      │        桌面应用（Electron / Tauri / 原生）      │
                      └───────────────┬─────────────────────────────┘
                                      │  统一 JSON 协议（文本 / 参考音频 / 参数）
                      ┌───────────────▼─────────────────────────────┐
   Windows ───────────►  ONNX Runtime 运行时 (C++/Python)            │
   Linux   ───────────►  · CPU EP（兜底）                            │
                      │  · CUDA EP（NVIDIA 快路径）                  │
                      │  · DirectML EP（AMD，可选）                  │
                      │  · 可选：onnxruntime-genai / llama.cpp(GGUF) │
                      └─────────────────────────────────────────────┘
                      ┌─────────────────────────────────────────────┐
   macOS   ───────────►  原生 Apple 运行时（二选一或两条腿）           │
   (M1–M5)            │  ① MLX（Swift / Python）— 主干大模型          │
                      │  ② CoreML + ANE — 小模型 & 声码器             │
                      │  ③ ONNX Runtime + CoreML EP（跨平台同一份）   │
                      └─────────────────────────────────────────────┘
```

**关键原则**：**不要让 macOS 版依赖 `torch.backends.mps`。** 理由（全部有实测）：
1. 算子缺失是**硬性**的（`>65536`、`aten::unfold_backward`、`float64`），不是性能问题；
2. 大模型在 MPS 上普遍 <0.5× 实时（M4 实测 IndexTTS-2 0.1×、F5-TTS ≤0.1×、Qwen3-TTS Base 0.2×）；
3. **静默回落到 CPU** 会让用户在不知情的情况下付 10 倍时间成本；
4. 维护者的官方立场普遍是劝退（ChatTTS、GPT-SoVITS），或干脆 `wontfix`（XTTS-v2）。

## 3.2 三条可选的产品路线（按交付难度排序）

### 路线 A（最快落地，最低风险）：**"许可干净 + 端侧可跑"组合**
| 平台 | 引擎 | 依据 |
|---|---|---|
| **macOS** | **Kokoro-82M via CoreML/ANE**（+ 可选 Piper ONNX） | M2 Studio 30 s 语音 379 ms（12–79× 实时，ANE），Apache-2.0 代码+权重，"Ship it. Sell it. Fork it."；tts-bench M4 上 MPS 13.8× / CPU 9.0× |

| 中文能力 | Kokoro 支持 zh（`zf_xiaobei` 等 4 女 4 男），但**中文自然度是 Kokoro 的相对弱项** | ⚠️ V2EX 用户原话："之前 **Kokoro 放出来的中文一言难尽**" |

## 3.3 落地检查清单（可直接当验收标准用）

1. **禁止静默回落**：任何引擎在目标设备不可用时，必须**显式报错或明确标记**，不能悄悄跑 CPU（VoiceStudio 的 spec 把这条列为硬规则，值得照抄）。
2. **Mac 上"显存"只能是估算**：`psutil.virtual_memory().total / 2`。不要基于 VRAM 做硬性限流。
3. **Mac 上并发只能是 1**：VoiceStudio 的环境变量文档原文 —— `MPS and CPU always get 1`；"**Do not raise this on ≤10 GB cards or Apple Silicon** — two concurrent jobs over-committing VRAM is exactly the crash class (#567) the auto-sizing exists to prevent."
4. **首次生成必然慢**：权重懒加载约 8 s，Apple Silicon 要预热 Metal kernel，MLX 还有 JIT kernel 编译（Kokoro MLX 首次 TTFA ~2057 ms vs MPS 595 ms）。**UI 必须给首帧进度**。
5. **MPS 假 OOM 的统一修法**：在 import torch 之前设 `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.0`。
6. **模型分阶段释放**：统一内存机器上，转写/合成模型不要同时常驻（VoiceStudio 默认 `OMNIVOICE_UNIFIED_OFFLOAD_HEADROOM_GB=6`）。
7. **Piper 音色必须逐条核许可**（`ryan/high` 是 CC BY-NC-SA 4.0）。
8. **不要把 F5-TTS / MaskGCT / XTTS-v2 / Fish-Speech / IndexTTS-* / Breeze / Echo-TTS / Higgs v3 / OuteTTS 预置进商业安装包**（全部有 NC 或自定义商用条款）。
9. **中文 TTS 必须单独测**：`H2` vs `2H`（IndexTTS 已知缺陷）、阿拉伯数字、标点、中英混读。CosyVoice3 的 `Pronunciation Inpainting` + `Text Normalization` 是唯一官方宣称覆盖这块的。
10. **两份榜单都要看但要打折**：TTS Arena V2 / Artificial Analysis 偏英文；tts-bench 有 Mac/Windows/Linux 三平台实测但客观分（UTMOS/WER/SIM）本次未抓到；中文必须用 CV3-Eval + 自己的盲测。

20. **第二批并行调研已完成**（覆盖 Dia / Higgs Audio v2 / VibeVoice / Zonos / Llasa / Step-Audio / Kimi-Audio / Qwen3-TTS / Qwen2.5-Omni / MOSS-TTSD / Chatterbox / NeuTTS / dots.tts / Kani / OuteTTS / Muyan / VoiceCraft / Seed-VC / OpenVoice），结论并入 **§2.11**；完整 18 行后端表见工作区根目录 `apple-silicon-tts-report.md`。**方法学限制**：GitHub REST API 被限流到 core 0/60，issue 正文与评论经 `curl` 解析页面内嵌 JSON 取得，发现渠道为 `web_search` + GitHub HTML 搜索而非完整 API 扫描，**低流量 issue 可能被漏掉**；Muyan-TTS 的 Apple 状态属于"没有证据"而非正面证据。**本批明确未核实项**：Llasa 的 MPS 行为与任何 M 系列性能；Muyan-TTS 在任何 Apple 后端上的表现；VoiceCraft / Seed-VC / OpenVoice 的非 PyTorch 路线；Qwen2.5-Omni 在 Apple 上的直接音频输出；**mlx-audio Qwen3-TTS 批吞吐表背后的硬件**（TPS 20.8–68.1、throughput 1.67×–5.45×、TTFB 78–140 ms、3.88–4.10 GB —— 数字有但硬件未标）；`CrispStrobe/CrispTTS` 的引擎宣称（README 在两个分支上均 404）；codersera.com 关于 Kimi-Audio on MLX 的说法。

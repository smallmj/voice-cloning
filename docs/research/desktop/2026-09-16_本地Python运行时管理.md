## 1. 嵌入式 Python 打包

### 1.1 uv 管理 Python 版本：可行，且已是 2025–2026 的主流

**结论：可行。** uv 能直接安装并管理 Python 解释器本身（`uv python install 3.12`），装在 `~/.local/share/uv/python/`，不污染系统 Python；也能 `uv venv` / `uv pip install` 管理虚拟环境与依赖。

版本节奏（说明项目处于高频可用状态）：0.9.0 发布于 2025-10-07，0.9.26 发布于 2026-01-15，0.11.0 发布于 2026-03-23，最新已到 0.12.9（2026-09-01）。

**中国大陆可用性是这个方案最大的软肋。** uv 默认从 GitHub 下载 python-build-standalone，国内会直接失败。这不是推测——ComfyUI Desktop issue 日志里就是原话：

```
& "C:\Program Files\ComfyUI\resources\uv\win\uv.exe" "venv" "--python" "3.12" "--python-preference" "only-managed"
error: Failed to download https://github.com/astral-sh/python-buil...
```

解法是 `UV_PYTHON_INSTALL_MIRROR`，社区已验证的可用镜像：

- 淘宝/阿里 npmmirror：`https://registry.npmmirror.com/-/binary/python-build-standalone`
- 南京大学：`https://mirror.nju.edu.cn/github-release/astral-sh/python-build-standalone/`

PyPI 侧则在 `~/.config/uv/uv.toml` 写 `[[index]] url = "..." default = true`。清华源官方给出的正是这个写法。

### 1.2 python-build-standalone（PBS）

- 2024-12-03 由 Gregory Szorc 移交 Astral 维护，Astral 用它作为 uv 的 Python 来源，并持续投入构建流水线改造；该项目「每次发布构建 947 个 artifact」。
- 产物是 `.tar.zst`（zstandard 压缩），供嵌入用的是 `install_only` 变体。
- **体积**：2026-09-01 的 release 资源列表显示单个 asset 落在 **23.1 MB – 41.9 MB** 区间（未逐平台核对哪个体积对应哪个平台/变体）。
- **平台**：macOS（aarch64 / x86_64）与 Windows x86_64 均有产物；精确平台矩阵未逐条核实，以 releases 页 asset 名为准。

### 1.3 conda / miniforge / micromamba 打包

- `conda-pack`：把 conda 环境打成可在其它机器/路径解开的归档，官方定位就是「where python and/or conda isn't already installed」。
- `constructor`：为一批 conda 包生成安装器（installer），定位是「delivery vehicles for the bundled packages」。
- `pixi`（prefix-dev/pixi）：Rust 写的跨平台包管理器，构建在 conda 生态之上，带 lockfile 与 task 系统；配套 `pixi-pack --environment prod --platform linux-64 pixi.toml` 产出 `environment.tar`，目标机用 `pixi-unpack` 还原。

**结论**：技术可行，但对「只想跑 PyTorch 的桌面 App」而言 conda 系的复杂度与体积不划算。唯一必须走 conda 的现实场景是 conda-only 包——典型例子是 CosyVoice 依赖链里的 `pynini`（WeTextProcessing 用），官方明确要求用 conda 装才能全平台可用。

### 1.4 真实产品怎么做的（本节最有价值的部分）

| 产品 | 推理引擎 | Python 环境管理方式 |
|---|---|---|
| ComfyUI Desktop（新版 Comfy-Desktop） | ComfyUI Python server | **自带 uv 二进制 + uv 托管 Python + 工作区 venv** |
| ComfyUI Portable（Windows） | ComfyUI | 内置独立 Python（`python_embeded`），解压即用 |
| Stability Matrix | PyTorch（多 WebUI 包） | 发布包 portable/self-contained；**每个包独立 venv**，Python 与 Git 随包分发 |
| Pinokio | 任意（脚本驱动） | 自带 Python / Node.js / Bun / Git / uv / Conda / Homebrew / FFmpeg / Caddy |
| LM Studio | llama.cpp (GGUF) + MLX | **没有 Python**（MLX 引擎用 mlx-lm / mlx-vlm 两个 Python 包，但整体是内嵌引擎） |
| Ollama | Go + GGML/llama.cpp | 无 Python（Go 通过 FFI 调 GGML）；2026-03-30 起 Apple Silicon 预览版改用 MLX |
| Jan | llama.cpp extension | 无 Python（llama.cpp extension 取代已废弃的 cortex.cpp） |
| GPT4All | C/C++ backend | 无 Python |

**关键洞察**：**LLM 类产品几乎全部绕开 Python**（C++/Rust/Go/内嵌引擎），因为它们的推理栈本身不是 Python 生态；而**TTS/声音复刻必须用 PyTorch，只能走「自带 uv + 托管 Python + venv + 运行时 pip install torch」这条路**。ComfyUI Desktop 是唯一公开源码、可直接抄作业的同构产品。

ComfyUI Desktop 的实证细节：源码 `src/virtualEnvironment.ts` 的文件头注释就是 "Manages a virtual Python environment using uv"，内部维护自己的 node-pty 实例把输出管道到虚拟终端；实测日志显示 `Using uv at C:\Users\robert\AppData\Local\Programs\ComfyUI\resources\uv\win\uv.exe`，以及 `Running uv command directly: pip install --dry-run ...`。

## 2. Sidecar 进程 + 本地通信范式

### 2.1 各产品架构

- **ComfyUI Desktop**：Electron 多进程（main / renderer）+ 独立 Python server 子进程；IPC 层负责两者通信；日志用 `electron-log` 全量记录，**主进程日志写 `main.log`、ComfyUI server 日志写 `comfyui_.log`**，路径为 macOS `~/Library/Logs/{app name}`、Windows `%AppData%\{app name}\logs`。这套「双文件 + 平台标准日志目录 + 内置终端」是被用户验证过可调试的范式。
- **LM Studio**：单进程 + 内嵌推理引擎，无 Python sidecar（与其 MLX 引擎架构文档一致）。
- **Pinokio**：`pinokiod` 守护进程 + 脚本引擎（Pinokio script 是可编程的 shell/JS 步骤描述）；`kernel/bin/index.js` 的 `Bin` 类统一管理 Python / Node / conda / uv 等外部二进制的安装与版本。
- **Stability Matrix**：.NET/Avalonia 桌面端；发布包不需要系统 Python / Git / .NET 运行时；自动为每个包建 venv 并装需要的 Python 版本与依赖，包环境互相隔离。

### 2.2 通信方式对比

- **本地 HTTP（FastAPI + uvicorn）+ WebSocket**：最主流。ComfyUI 走 `127.0.0.1:8188` 的 HTTP + WebSocket 推送进度。优点：任何语言都能调、易调试、易做流式音频。缺点：要管端口、要管鉴权。
- **stdio JSON-RPC**：无端口、无防火墙弹窗；但无法多路复用，音频等大二进制要 base64（膨胀 33%），且协议流与日志流混在同一个 stdout 上难以分离。
- **gRPC**：已有 stdio / Unix domain socket / file 传输的现成实现与跨语言对照（Go/Python），但对 Electron 侧要引入 proto 生成与 grpc-web，收益不明显。
- **ZeroMQ**：延迟低，但引入原生依赖，打包与签名负担加重。gRPC 与 ZMQ 的吞吐/延迟对比有第三方论文，但结论依赖测试条件，不作为选型依据。
- 厂商宣称的「JSON-RPC over io_uring 比 FastAPI 低 50x 延迟」属厂商自述，**未独立核实**。

**坑（每条都有来源）**：

1. **端口占用**：ComfyUI 默认 `127.0.0.1:8188`，多开会报 `Port 8188 is already in use on address 127.0.0.1`。正确做法是 **bind port 0 让 OS 分配**——Discobot、argent、gitchorus 等多个 Electron 项目都实现了 `listen(0, "127.0.0.1")` 再回传真实端口的 `findAvailablePort()`，目的就是消除 `EADDRINUSE` 与同类应用冲突。
2. **防火墙弹窗**：Electron 在 Windows 上会触发防火墙警告（electron#23756 是 WebRTC/UDP 触发的）；SO 上也有「Electron TCP server 在 Windows 被防火墙拦截、必须关防火墙才通」的案例。**绑 127.0.0.1（而非 0.0.0.0）+ 动态端口能大幅降低触发概率**。
3. **本地端口安全（最常被忽略）**：`127.0.0.1` 上的服务对本机所有进程（包括任意浏览器页面）可见，必须用主进程启动时生成的 opaque/bearer token 经环境变量注入 sidecar、前端带上才能调用——executor 与多个 Electron 项目都采用这个模式；amd/gaia 的 issue 也把「本地 REST API 无调用方鉴权」列为待修的安全问题。
4. **进程孤儿**：Node 的 `child.kill()` 只杀直接子进程，Windows 上孙进程会存活（SO 57449252 用 Electron+Python+Flask 复现）；需要 Windows-aware teardown（hermes-agent 的 `backend-child.ts` 就是现成实现）。另注意 Node 的 `child.killed` 只表示「信号发送成功」，不代表进程已退出，不能用于清理判断。
5. **杀软拦截**：PyInstaller 打出的 exe 被 Windows Defender 误报为木马（SO 78256586），根因是 bootloader 的自解压落盘行为与恶意软件特征重合，属打包方式问题而非代码问题。

### 2.3 可复用的现成组件（逐个核实过）

| 组件 | 结论 | 证据 |
|---|---|---|
| **uv** | ✅ 推荐。Rust CLI（非库优先），子进程调用即可，ComfyUI Desktop 就这么用 | virtualEnvironment.ts / 实测日志 |
| **pixi + pixi-pack** | ✅ conda 路线可用，lockfile 可复现，`pixi-pack`/`pixi-unpack` 做交付 | pixi 文档 |
| **PyApp (ofek/pyapp)** | ⚠️ 适合纯 Python 自举，**预构建发行版来源就是 python-build-standalone**，`PYAPP_DISTRIBUTION_EMBED=1` 可把发行版嵌进可执行文件；不适合带 torch 的主流程 | ofek.dev/pyapp |
| **conda-pack / constructor** | ✅ conda 路线可交付 | 官方文档 |
| **pex** | ❌ 对 torch 实测失败：`torch._C import * ... cannot open` | pex#2388（2024-03-21） |
| **shiv** | ❓ PEP 441 zipapp；对含大量二进制扩展的 torch 是否可用**未核实** | linkedin/shiv |
| **PyInstaller** | ❌ 不要把 torch 打进去：打包后体积约 4GB，跨机运行 `from torch._C import * ImportError: DLL load failed` | #8551（2024-05-21）、#5676 |
| **Nuitka** | ❌ torch 触发 anti-bloat 报错；standalone 下 Torch JIT 默认禁用 | Nuitka#3288（2025-01-09） |
| **Briefcase (BeeWare)** | ⚠️ MSI 安装器对超大文件（torch + CUDA）有已知限制，安装会失败 | briefcase#1788（2024-05-11） |

**核心结论：没有任何「打包器」能把 torch 干净地冻进去。正确姿势是「分发 Python 运行时 + venv + 运行时 pip install」，而不是冻成单文件。**

## 3. 模型下载 / 校验 / 断点续传

### 3.1 huggingface_hub 现状（2025-10 是分水岭）

- `snapshot_download()` 下载整仓，内部走 `hf_hub_download()`，因此文件同时进本地缓存；下载是并发的。
- 参数 `resume_download` 在 0.23.0 被弃用，官方口径是「所有下载默认支持续传」。
- **huggingface_hub v1.0.0（2025-10-24 发布，博客 2025-10-27）**：底层迁移到 httpx；`hf` CLI 取代已弃用的 `huggingface-cli`（Typer 实现）；**全面采用 `hf_xet` 做文件传输**；`hf_transfer` 支持被移除、`HF_HUB_ENABLE_HF_TRANSFER` 环境变量被忽略，改用 `HF_XET_HIGH_PERFORMANCE`。
- Xet 存储：2025-03-18 官宣「Xet is on the Hub」；2025-07-15「Migrating the Hub from Git LFS to Xet」，半年内迁移 50 万个仓库。

**断点续传的真实坑（必须知道）**：

- huggingface_hub#3007（2025-04-15）：`snapshot_download` 在 resume 时忽略 5xx 错误，**返回不安全的缓存数据**。
- huggingface_hub#4196（2026-05-06）：`hf download` 被中断后重跑会从头开始，**不续传**。
- PR #4143「Harden resume validation」（2026-04-24）：给 `.incomplete` 文件持久化 resume 元数据，并用 `If-Range` / `Content-Range` 校验通过后才追加数据。**这意味着在此之前存在「把残缺文件当完整文件」的风险；客户端应锁定到含该修改之后的版本（具体版本号未核实）。**

### 3.2 中国大陆镜像（本节结论很硬）

- `hf-mirror.com` + `HF_ENDPOINT=https://hf-mirror.com` 是标准做法，站方定位是「公益项目，帮助国内 AI 开发者快速稳定下载模型、数据集」。
- **关键坑：Xet 流量不走 `huggingface.co`，而走 `cas-server.xethub.hf.co`，`HF_ENDPOINT` 覆盖不到**（huggingface_hub#4475）。所以国内环境必须 `HF_HUB_DISABLE_XET=1` 强制回落普通 HTTP 下载。
- **但 hf-mirror 用户报告 `HF_HUB_DISABLE_XET=1` "好像不生效"**（padeoe/hf-mirror-site#64，日期未核实）。
- **结论：国内分发的下载层必须自研，不能假设官方客户端的镜像变量与关闭开关一定生效。** 合理做法是国内默认走 ModelScope，HF 只作为兜底。
- ModelScope 官方 CLI 契约：`modelscope download --model <id> [--revision] [--cache_dir] [--local_dir] [--include] [--exclude] [files...]`。

### 3.3 下载器组件

- **aria2**：`-x 16 -s 16` 多连接分块并行，支持 Metalink 分块校验（下载中自动验证数据块）、session 文件续传，内存占用 4–9 MiB。
- **社区 HF+aria2 下载器**：`han-xudong/hf_downloader`、`bughoho/hfdownloader`（`hfd.sh`，基于 aria2/wget）均支持用 aria2 的 session 文件做断点续传地拉整个仓库。
- **磁盘空间检查 / SHA256 校验**：HF 缓存本身是 CAS（内容寻址），`http_get` 内部有 `expected_size` 校验；但桌面端仍需自建「下载前查磁盘余量 + 下载后按固定 SHA256 清单校验」。具体的校验覆盖范围**未核实**。

## 4. Apple Silicon 上跑 PyTorch TTS 的现实体验

### 4.1 MPS 后端的支持缺口（TTS 是重灾区）

- 官方跟踪入口：MPS operator coverage tracking issue #141287（2.6+，2024-11-21）；Most requested ops #154052（2025-05-21）；第三方每日更新的覆盖矩阵 `qqaatw.dev/pytorch-mps-ops-coverage`。
- `PYTORCH_ENABLE_MPS_FALLBACK=1` 的语义是「未实现的算子自动落 CPU」，**但对部分算子不生效**：pytorch#134416 显示 `nn.Conv1d` 仍抛 `NotImplementedError: Output channels > 65536 not supported at the MPS device`。
- **TTS 的核心报错就是这一条**：coqui-ai-TTS#248（2025-01-09）、coqui-ai/TTS#4124（2025-01-04）报的都是 `Output channels > 65536 not supported at the MPS device`，建议的临时手段正是 `PYTORCH_ENABLE_MPS_FALLBACK=1`——而它对 Conv1d 无效。
- XTTS v2 在 MPS 上直接 hang：coqui-ai/TTS#3649（2024-03-28），用户是 M1 Max / 32 核 GPU / 64GB 统一内存，「it just hangs」。

### 4.2 各 TTS 项目在 Mac 的实际状态

| 项目 | Mac 状态 | 证据 |
|---|---|---|
| **GPT-SoVITS** | 官方建议 Mac 上用 CPU。维护者口径：MPS 有内存泄漏，且 MPS 训练出来的声音质量显著更差，「等 PyTorch MPS 优化好后再用 GPU」。install.sh 支持 `--device MPS\|CPU`，社区另有 CPU 专用裁剪分支 (GPT-SoVITS-CPUFast) | issue #808（2024-03-18）；中文部署教程（2025-09-09） |
| **IndexTTS / IndexTTS2** | MPS 报同类错误；macOS 最佳实践是禁 DeepSpeed/CUDA kernel、开 FP16、用 Metal 优化版 torch。官方仓库明确「仅支持 uv，conda/pip 可能导致依赖不正确」 | index-tts#351；macOS 性能文章（2026-04-07/08）；官方 README_zh |
| **CosyVoice** | 依赖 pynini，官方要求 conda 安装；pip 编译 pynini 在 Windows/Linux 失败。社区有 MPS fork（jasper11452/CosyVoice-mps，宣称原生 MPS 加速） | CosyVoice#528（2024-10-20）；pypi 说明 |
| **Fish Speech** | #356 询问 macOS 支持；#789 MPS dtype mismatch（2024-12-27）；#790 修了 dtype 但 API 仍 500。官方 changelog v1.1.1 提到加入 Apple Silicon (MPS) 支持、Windows 一键安装、带续传的自动模型下载（日期未核实） | fish-speech#356 / #789 / #790；Fish Audio changelog |

**结论：Mac 上「能跑」和「可用于产品」差距很大。** GPT-SoVITS / IndexTTS 这类含 BigVGAN / Conv1d 上采样结构的方案，在 MPS 上至今有硬伤。

### 4.3 CUDA-only 依赖在 macOS 上必然失败

- **fairseq**：M1 安装直接报错（fairseq#5448，2024-03-02）。
- **fairseq2**：M1 Pro 全新环境装不上（fairseq2#211，2023-12-11）。
- **DeepSpeed**：官方只有 python-only 预览分支能绕开 CUDA/C++ 要求，且该模式下 Lamb 与 FusedAdam 不支持（DeepSpeed#130，2020-03-10）。
- **flash-attn**：不支持 Apple silicon（flash-attention#770，2024-01-15）；LLaVA#698 中 M1 Max 用户 `pip install flash-attn --no-build-isolation` 直接失败（2023-10-29）。

**产品含义：安装器必须能按平台把 deepspeed / flash-attn / fairseq 这类包从依赖里剔除或降级为 optional-extras，否则 macOS 上 pip 在解析阶段就会炸。**

### 4.4 CPU/RTF 量级参考

- Kokoro 82M：RTF **0.03**，显存 **<1 GB**（CodeSOTA 对比表，2026-03-28）。
- XTTS v2：RTF **0.18**，显存 **~4 GB**（同上）。
- qwen3-tts 在 Apple M1 8 核 / 16 GB 上：0.6B bf16 RTF **≈1.3–1.7**（慢于实时）；0.6B `--int8` RTF **<1.0**（CLI / 流式 / HTTP server 均 <1）。
- Metal 后端：0.6B 在 M1 上 RTF **1.5 → 0.60**、M2 Pro **0.36**，流式首包 314 ms；CUDA 上 1.7B RTF **0.44**（RTX 4060 级）到 **~0.12**（4090）。

注意：这些 RTF 来自不同项目的自测、模型不同，**不可直接横比，只能看量级**。

## 5. 显存/内存不足的降级策略

### 5.1 可用策略（按性价比排序）

1. **fp16 / bf16**：IndexTTS2 在 macOS 的最佳实践里 `--fp16` 被标为「必开」。
2. **量化 int8 / AWQ-int4**：CosyVoice3 有社区 AWQ 4-bit 实现（降低精度到 4-bit，显著减少显存并提速）；实测 FP32 2.3 GB → FP16 1.1 GB → INT8 0.6 GB → AWQ-INT4 0.3 GB，但 MOS 从 4.2 掉到 3.5（**质量换显存是明确的**）。
3. **CPU offload**：HuggingFace accelerate 的 `cpu_offload` / `device_map`，官方语义是「全部参数卸载，state dict 只保留一份，forward 时按需取参数上设备」。
4. **分块推理 / 降低 batch / 关闭 KV cache / 懒加载**：IndexTTS#411 里对「OOM 后显存不释放」的建议就是懒加载。
5. **卸载到磁盘**：未找到可引用的成熟桌面端实现，**未核实**。

### 5.2 显存需求估算（均为来源实测或官方口径，落地前需自测）

| 模型 | 显存口径 | 来源 |
|---|---|---|
| Kokoro 82M | < 1 GB | CodeSOTA 表（2026-03-28） |
| XTTS v2 | ~4 GB | 同上 |
| GPT-SoVITS | 官方：支持 CUDA 的 NVIDIA 显卡、**每张 ≥6 GB 显存**；另有实测推算「不开 KV cache + half + 单句短文本，理论最小 3–3.5 GB」 | 官方飞书 wiki；心居网（2026-04-23） |
| CosyVoice3 | 参数 >3 GB，「峰值显存轻松突破 6 GB，低于 8 GB 显存几乎无法稳定运行」；另一口径 FP32 整体占用 2.3 GB | CSDN 实测（2026-01-01）；GitCode（2026-02-04） |
| IndexTTS2 v2 | 3060 12G 用户反馈「15 秒音频需要 30 多秒推理，基本 2 倍推理时间」，OOM 后需重启 | index-tts#411（2025-09-19） |

**桌面端最低门槛建议定在 6–8 GB 显存；4 GB 卡只适合 Kokoro 这类小模型。**

### 5.3 优雅检测与提示

- **NVIDIA**：`nvidia-smi`；`torch.cuda.mem_get_info()`；`pynvml`（nvidia-ml-py3）直接查 NVML，比包 nvidia-smi 快得多。PyTorch 官方「Understanding CUDA Memory Usage」明确建议：用 pynvml 采集 PyTorch 之外的分配量来对账。
- **Apple**：`torch.mps.recommended_max_memory()` 拿统一内存下的推荐上限；MPS 专有环境变量见官方 `mps_environment_variables` 页。
- **产品化**：启动前先探测（显存总量 vs 模型需求），不够就在 UI 上给「切 int8 / 切 CPU / 换小模型」三选项，而不是等 OOM 崩掉。
- **必须做进程隔离**：index-tts#411 用户反馈「显存不足报 OOM 后没有清空，只能重启」——这是「sidecar 必须可整体重启」的硬理由。

## 6. Windows 上的 CUDA / cuDNN / VC++ 运行时分发

### 6.1 要不要用户自己装 CUDA Toolkit

**不需要。** PyTorch 官方原文：「The PyTorch pip wheels and conda binaries ship with all needed CUDA dependencies and thus no locally installed CUDA toolkit is needed and used unless you build PyTorch from source or custom CUDA extensions.」——用户只需要装正确的 NVIDIA 驱动。

### 6.2 驱动版本要求

CUDA 11 起引入 **Minor Version Compatibility**：同一 CUDA 大版本族内编译的应用，可在满足最低驱动版本的机器上运行（功能集有限）。CUDA 12.x 的 Windows 最低驱动为 **>= 525**（NVIDIA 官方兼容性文档表 1）。

**产品含义：安装向导必须检查「驱动版本」，而不是检查「有没有装 CUDA Toolkit」。**

### 6.3 PyTorch Windows wheel 的 CUDA 版本对应（2025→2026 变化很快）

- **PyTorch 2.10**（wheel variants 邮件列表，2026-02-05）：支持 CUDA **12.6 / 12.8 / 13.0**（Linux x86、Linux aarch64、Windows x86），另有 ROCm 7.0/7.1、XPU、CPU-only、macOS（含 M1/M2）。
- **PyTorch 2.11**：**CUDA 13 成为 x86_64 与 ARM 的默认**；CUDA 12.8 仍可从对应 index 子目录取；release 说明中提到 CUDA 12.8 binaries 已从构建矩阵移除、CUDA 13.0 为稳定默认、CUDA 12.6 保留给老驱动用户。
- **PyTorch 2.14**（release blog，2026-09-02）：CUDA **12.6 / 13.0 / 13.2**，默认仍为 **13.0**；安装命令 `pip3 install torch --index-url https://download.pytorch.org/whl/cu130`。
- **Python 支持**：2.10 为 `>=3.10, <=3.14`（3.14t 实验）；2.14 为 `>=3.10, <=3.15`（3.15t 实验），C++20。

**产品含义：不要写死 `cu121`。** 要么按驱动版本动态选 `--index-url`，要么默认 CUDA 12.6（兼容老驱动）+ 高级选项切 13.0，并让用户可覆盖。ComfyUI 官方就是双包策略：portable 新包 = **Python 3.13 + PyTorch CUDA 13.0**，老卡包 = **Python 3.12 + cu126**。

### 6.4 常见坑（每条有来源）

| 坑 | 事实 | 来源 |
|---|---|---|
| **pip 装成 CPU 版 torch** | PyPI 不托管 CUDA 构建，裸 `pip install torch` 会解析到 CPU-only wheel，安装成功但 `torch.cuda.is_available()` 为 False | Latchkey Learn（2026-06-30）；pytorch#168065（2025-11-18） |
| 上述坑的真实产品翻车 | ComfyUI Desktop 0.7.2 用户（CUDA 13.0）安装后 `AssertionError: Torch not compiled with CUDA enabled` | ComfyUI 论坛（2026-01-12） |
| **VC++ Redistributable** | PyTorch Windows 官方文档原文：「since we didn't pack some libraries and VS2017 redistributable files in, please make sure you install them manually」；报错文案是 `Microsoft Visual C++ Redistributable is not installed, this may lead to the DLL load failure` | PyTorch Windows FAQ；pytorch#126507（2024-05-16）；微软最新支持页（2026-03-09） |
| **DLL load failed** | `from torch._C import * ImportError: DLL load failed`，官方 FAQ 归因为缺少必要文件；PyInstaller 跨机打包同样命中 | PyInstaller#5676 |
| **中文路径** | `torch.save` 使用中文文件名会输出乱码 | pytorch#98918（2023-04-12）；#90040 |
| **杀毒软件拦截** | 未签名的 PyInstaller onefile exe 被 Defender 报毒，根因是 bootloader 解包到临时目录再执行的行为与恶意软件重合 | SO 78256586（2024-04-01）；pyobfuscate（2026-09-01） |

## 7. 其他：国内网络环境下首次安装的体验优化

ComfyUI Desktop 的中文文档给出了官方做法，可直接抄：

- **设置里提供「Python 安装镜像」**：托管的 Python 安装包下载自 Astral python-build-standalone；可设置镜像 URL 替换默认 GitHub 下载地址；**支持 `file://` 协议从本地目录读取发行包**；并自动检查镜像可达性。
- **「PyPI 镜像 URL」**（示例给的是 `https://mirrors.aliyun.com/pypi/simple/`）；另有「使用中国镜像（Git & PyPI）」总开关与缓存目录设置。
- 官方社区讨论 #390（2025-08-28）对国内用户的建议是改用 portable / 整合包 —— **反过来说，「离线 / 预打包运行时」在国内不是可选项，而是主路径**。

其他可组合的手段：`UV_PYTHON_INSTALL_MIRROR`（npmmirror / 南大）、`uv.toml` 默认 index、`HF_HUB_DISABLE_XET=1` + `HF_ENDPOINT=https://hf-mirror.com`、ModelScope 作备选模型源、aria2 做多线程分块续传、以及魔当（LM Downloader，开源，仓库 2025-02-12）这类「环境+模型」一键工具——它是国内同类产品的直接参照。

# 推荐方案

## 首选：自带 uv + 托管 Python(PBS) + 每实例独立 venv + 运行时 pip install torch + 本地 HTTP/WS sidecar

1. **Electron 主进程启动时先探测**：GPU 型号 / 驱动版本 / 可用显存 / 磁盘余量 / 网络可达性，再决定 Python 版本与 torch 后端。
2. **用随包分发的 uv**（`resources/uv/{win,mac}/uv`）执行 `uv venv --python 3.12 --python-preference only-managed` —— 策略照抄 ComfyUI Desktop，但加镜像兜底。
3. **首次启动前就注入镜像**：`UV_PYTHON_INSTALL_MIRROR`（npmmirror / 南大）→ uv.toml PyPI index → 失败时可切 `file://` 本地 PBS 包。
4. **显式指定 torch 索引**：`uv pip install torch --index-url https://download.pytorch.org/whl/cu126|cu130`（按驱动版本选）；macOS 用默认 wheel，并在依赖解析阶段剔除 deepspeed / flash-attn / fairseq。
5. **Sidecar 用 FastAPI/uvicorn，bind `127.0.0.1:0` 动态端口**；主进程生成 bearer token 经环境变量注入，前端带 token 调用。日志用 electron-log 双文件（`main.log` / `python.log`），落地到平台标准日志目录。
6. **自研模型下载层**：国内优先 ModelScope → HF（hf-mirror + 关 Xet）→ aria2 分块续传兜底；下载前检查磁盘，下载后按固定 SHA256 清单校验。
7. **每个实例 = 一个 venv + 一个 sidecar 进程**，可整体重启（不要在同一进程内反复重载模型，OOM 后显存可能不释放）。

## 备选

- **A. 预打包离线运行时（国内主推）**：模仿 ComfyUI Portable，把 PBS Python + venv + torch wheel 全塞进安装包或 `file://` 镜像目录，首次启动零下载。对国内首次体验提升最大；代价是安装包 +2~4 GB，且需按 GPU 后端各出一个包。
- **B. conda 路线（pixi + pixi-pack）**：仅在必须用 conda-only 包（pynini 等）时采用；用 pixi lockfile 保证可复现，`pixi-pack`/`pixi-unpack` 做交付。
- **C. PyApp**：若 sidecar 是纯 Python CLI 且不含 torch，PyApp 能给出很小的自举可执行文件（发行版来源同为 PBS）。**不适合带 torch 的主流程。**

**明确不推荐**：PyInstaller onefile 打 torch（4 GB + DLL load failed）、briefcase MSI 装 torch+CUDA、pex 装 torch、Nuitka 编译 torch。

# 坑清单（可执行 checklist）

**打包与首次启动**
- [ ] 绝不依赖系统 Python；用 `--python-preference only-managed` 强制托管 Python

- [ ] 失败后清理半成品 `.venv`（ComfyUI#1574 的教训），避免重试踩坏环境
- [ ] Python 进程退出码写进日志并可辨识（3221225477 / 0xC0000005）
- [ ] macOS 侧在依赖解析期就排除 deepspeed / flash-attn / fairseq / BigVGAN CUDA kernel
- [ ] 安装目录强制 ASCII，处理中文与空格路径
- [ ] 随包静默安装 VC++ Redistributable
- [ ] 代码签名（避免 Defender 误报）
- [ ] 不使用 PyInstaller onefile 打 torch

**运行时**
- [ ] sidecar bind `127.0.0.1:0` 动态端口 + bearer token 鉴权
- [ ] Windows-aware 进程树 teardown（`child.kill()` 不够）
- [ ] 启动前探测显存 / 统一内存，不足时给降级选项而非等 OOM
- [ ] OOM 后可整体重启 sidecar
- [ ] 主进程 / 推理进程日志分离，提供「导出诊断包」

**模型下载**
- [ ] 国内默认 ModelScope；HF 路径必须 `HF_HUB_DISABLE_XET=1` + `HF_ENDPOINT=https://hf-mirror.com`
- [ ] 锁定 huggingface_hub 到含 resume 硬化（PR #4143）之后的版本

- [ ] 断点续传 + 失败重试 + 可恢复的下载队列（aria2 session）

- [ ] GPT-SoVITS 系在 Mac 上默认 CPU

**Windows CUDA**
- [ ] 不要求用户装 CUDA Toolkit，但必须检查驱动最低版本（CUDA 12.x → >=525）
- [ ] 显式 `--index-url`，绝不裸 `pip install torch`

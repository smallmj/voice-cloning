## 0. 结论先行

### 0.1 v1 默认引擎：**IndexTTS-2.5**（bilibili IndexTeam）

**一句话理由**：在所有满足「可商用 + 零样本复刻 + 中文强」的候选里，**只有 IndexTTS-2.5 把「用 uv 在 Windows CUDA 上装起来」当成一等需求来做**——官方发布 `uv.lock`、`pyproject.toml` 里为 win32 单独写了分支（`wetext` 替代 `WeTextProcessing`、`triton-windows` 替代 `triton`、`[tool.uv.extra-build-dependencies]` + `match-runtime` 让 flash-attn 走预编译 wheel 而不是现场编译），README 里明写「Windows 上 DeepSpeed 较难安装，请去掉 `--all-extras`」。这与我们的运行时约束（uv + 每实例 venv + `uv pip install torch --index-url ...`）几乎逐字对齐。

| 维度 | 实测/一手结论 |
|---|---|
| 显存 | **约 6 GB**（HF 模型卡原文："an NVIDIA GPU, and roughly 6 GB of VRAM for inference"）→ 8GB 卡可跑 |

### 0.2 v1.1 效果档：**VoxCPM2**（OpenBMB）

**Apache-2.0（代码+权重，官方明写 "free for commercial use"）**、`pip install voxcpm` 一条命令、seed-tts-eval **test-zh CER 0.97 / SIM 79.5**（开源模型里并列最高之一）、**音色设计（Voice Design）开箱即用**、48kHz 输出、30 语言 + 9 种中文方言。代价：约 **8 GB** 显存、RTF ~0.30（4090）、依赖树比 IndexTTS 重（`funasr` / `datasets` / `gradio>=6` / `spaces` 等），且自述 `Development Status :: 3 - Alpha`。

它与 IndexTTS-2.5 是**互补**关系：IndexTTS 赢在安装确定性与显存下限，VoxCPM2 赢在许可证洁净度、相似度上限与「音色设计」能力。因此建议 v1 用 IndexTTS-2.5 打通闭环，v1.1 把 VoxCPM2 作为「效果档 / 无需参考音频的音色设计档」并行上线。

### 0.4 三条最重要的单点发现

1. **`pynini` 没有 Windows wheel** —— 这是本轮调研中最锋利的筛子。PyPI `/simple/pynini/` 的 wheel 平台分布实测为：`manylinux_2_28` × 78、`manylinux2014` × 24、`manylinux_2_17` × 24、`manylinux_2_27` × 20 —— **146 个平台 wheel 全部是 manylinux，`win_amd64` 与 `macosx` 均为 0**。唯一的非平台 wheel 是 2015 年前后的 `pynini-0.4.x-py3-none-any`，**满足不了 `pynini>=2.1.6`**。凡**基础依赖**写 `WeTextProcessing` 的项目（实测：**MegaTTS3**、**dots.tts**），在 **`uv pip install` 解析依赖时就会失败**；而 conda-forge 的 `pynini` 救不了我们（运行时是 uv，不是 conda）。IndexTTS 官方正是用 `wetext; sys_platform != 'linux'` 绕开它（该做法源自社区 issue #150）——**这是官方主动为 Windows 用户做的适配**，含金量极高。CosyVoice 当前 `requirements.txt` 也已改用 `wetext==0.0.4`，不受影响。
2. **IndexTTS-2.5 的 `[tool.uv.extra-build-dependencies]` 是教科书级做法**：`deepspeed`/`flash-attn` 用 `{ requirement = "torch", match-runtime = true }` 让 uv 按 CUDA 版 torch 去匹配**预编译 wheel**，从而绕开 flash-attn「现场编译、吃满内存、动辄失败」的经典陷阱。我们自研封装若走 flash-attn 路线，应照抄这个模式。
3. **显存是真的会被占住的**：IndexTTS issue #649（2026-02-06）报告「一直挂着 index-tts 就持续占 **10GB** 显存，导致跑不了别的工具」。注意这与 HF 卡上的「约 6GB 推理显存」不矛盾——常驻 + 情绪模型（QwenEmotion）会把占用推高。**产品必须提供「卸载模型 / 释放显存」能力，不能假设进程常驻是免费的。**（同项目 #630 给出了泄漏的完整时间线，见 §0.5）

### 0.5 ⚠️ 与本项目运行时约束**正面冲突**的一个失败模式：传递依赖把 CUDA torch 顶掉

这是本轮调研中**对「自带 uv + 每实例 venv + `uv pip install torch --index-url ...`」这个架构威胁最大的一条**，值得单独列出。

**一手证据 —— VoxCPM issue #60**（2025-10-03，标题 *"Voxcpm not using GPU, and hence generation time is 700s for 29second clip"*，RTX 3060 6GB 笔记本，**Windows**）：
> *"Still every time torch shows **2.8.0+cpu** and CUDA unavailable. ... We suspect **FunASR/ModelScope auto-installs CPU torch over GPU build** or sys.path picks up CPU torch."*
>
> 用户已尝试：改 `app.py` 的 device、`--device cuda`、手动装 GPU wheel、卸载 CPU torch、装 `torch-2.5.1+cu121` / `torchaudio-2.5.1+cu121`、反复重装、确认 `nvidia-smi` 正常（driver 581.29 / CUDA 13.0）——**全部无效**，最终 **29 秒音频跑了 700 秒**（RTF ≈ 24）。
> https://github.com/OpenBMB/VoxCPM/issues/60

**机制**：`funasr` / `modelscope` 这类传递依赖在解析时会从**默认 PyPI 索引**取 `torch`，而默认索引上的 `torch` 是 **CPU-only wheel**。一旦它先进了 venv，我们指定的 CUDA 版就被顶掉（或被 `sys.path` 里的另一份遮蔽），表现为「明明装了 GPU 版，`torch.cuda.is_available()` 却是 False」。

**IndexTTS 官方对此有直接对策** —— `pyproject.toml` 里那段注释读起来就是针对这个坑写的：

```toml
[tool.uv.sources]
# Install PyTorch with CUDA support on Linux/Windows (CUDA doesn't exist for Mac).
# NOTE: We must explicitly request them as `dependencies` above. These improved
#       versions will not be selected if they're only third-party dependencies.
torch      = [{ index = "pytorch-cuda", marker = "sys_platform == 'linux' or sys_platform == 'win32'" }]
torchaudio = [{ index = "pytorch-cuda", marker = "sys_platform == 'linux' or sys_platform == 'win32'" }]
torchvision= [{ index = "pytorch-cuda", marker = "sys_platform == 'linux' or sys_platform == 'win32'" }]

[[tool.uv.index]]
name = "pytorch-cuda"
url = "https://download.pytorch.org/whl/cu128"
# Only use this index when explicitly requested by `tool.uv.sources`.
explicit = true
```

翻译成工程要求就是三条：
1. **`torch` / `torchaudio` 必须写成 project 的「直接依赖」**，不能只靠 `torch` 作为别人的传递依赖被带进来——否则「改进过的版本不会被选中」（官方注释原文）。
2. CUDA 索引要**显式声明**并设 `explicit = true`（不要用 `--extra-index-url` 那种「两个索引平级、谁版本高选谁」的写法；`--extra-index-url` 正是 CPU wheel 能溜进来的通道）。对照：**CosyVoice 的 `requirements.txt` 用的正是 `--extra-index-url https://download.pytorch.org/whl/cu121`**，属于更容易出这个问题的写法。
3. **安装后必须做一次运行时自检**：断言 `torch.cuda.is_available()` 且 `torch.version.cuda` 非空，否则**拒绝启动并在 UI 上给出明确报错**——而不是让用户跑到「29 秒音频 700 秒」才发现。

**对 v1 的直接含义**：IndexTTS-2.5 的 `pyproject.toml` 已经把这三条做完了。**这是把 IndexTTS-2.5 定为 v1 的最强工程论据——比任何 CER/SIM 数字都更贴合我们的运行时约束。**

### 2.2 关于 RTX 3090 的 RTF：**推算，非实测**

**本次调研没有找到任何一条 IndexTTS / VoxCPM2 / Qwen3-TTS / CosyVoice3 在 RTX 3090 上的官方实测 RTF。** 官方公布的卡型只有 **RTX 4090**。因此：

- 表中 3090 相关数字我**不填**，只给 4090 一手值。
- 若要预判，可参考以下**推理**（**未经实测验证，禁止当成结论写进对外材料**）：3090 显存带宽 ~936 GB/s vs 4090 ~1008 GB/s（差距约 7%），而自回归 TTS 解码阶段是**访存瓶颈**而非算力瓶颈；故 3090 的 RTF 大概率在 4090 值的 **1.05–1.35 倍**区间。IndexTTS-2.5 若为 0.21（4090）→ 3090 约 **0.22–0.28**；VoxCPM2 若为 0.30 → 3090 约 **0.32–0.40**。
- **落地动作**：v1 上线前必须在真实 3090 上跑一遍 `tools/gpu_check.py` + 官方 RTF 口径，把数字补齐到本文档。

### 2.3 一条必须记住的真实 Windows 反例（一手）

- **IndexTTS issue #585**（2025-11-30，标题 *"Index TTS 2 slow on RTX 3060 12gb VRAM"*，**Windows 10** + RTX 3060 12GB + 16GB RAM）：
  生成 **17.38s** 音频耗时 **227.86s** → **RTF 13.11**。分项：`gpt_gen 54.36s` + `s2mel 141.85s` + `bigvgan 9.35s`。
  URL: https://github.com/index-tts/index-tts/issues/585
- **读法**：这不是模型不行，而是**默认未开半精度 + 未装 CUDA 内核加速**的后果（日志里没有 fp16/bf16，且 3060 上 `s2mel` 占 142s 是典型的 fp32 未加速特征）。它恰好证明：**半精度开关不是可选项，而是产品必须默认打开的项**。同时也解释了官方 README 为什么反复强调 FP16/BF16。
- **对产品的直接含义**：我们的运行时封装必须把 `use_bf16=True`（2.5）/ `use_fp16=True`（2.0）**设为默认**，并提供 `tools/gpu_check.py` 式的自检，把「用户装完发现慢 60 倍」这类支持工单挡在前面。

#### 3.1.2 中文效果

- IndexTTS-2（1.5B）seed-tts-eval test-zh **CER 1.03 / SIM 76.5**（三方模型卡一致，见 §2.4）。
- **IndexTTS-2.5 自身独立的 seed-tts-eval 数字：未核实**（2.5 的 HF 卡与 GitHub README 均未附完整评测表，只声明「与 2 相当」）。**不要把 2.0 的数字直接标成 2.5 的数字对外。**
- 中文可控性（**这是它相对其他候选最实用的差异点**）：官方支持 **拼音显式注音**解决多音字，语法 `<行|XING2>`：
  ```python
  tts.infer(spk_audio_prompt="prompt.wav",
            text="他在银<行|XING2>里<行|HANG2>走了半天。",
            lang="ZH", output_path="output.wav")
  ```
  英文支持 CMU 音素，日文支持假名。**中文社区长期抱怨的「多音字读错」，IndexTTS-2.5 给了官方语法级解法**——VoxCPM2 / MOSS-TTS / LongCat 目前均未见等价能力。
- 语速控制 `duration_factor`（0.5–2.0）、情感参考音频 / `emo_alpha` / 8 维情感向量（顺序 `[高兴, 愤怒, 悲伤, 害怕, 厌恶, 忧郁, 惊讶, 平静]`）。

#### 3.1.3 零样本复刻能力

- 单条参考音频即可，**不需要参考文本转写**（`spk_audio_prompt`）。这比 CosyVoice3 与 LongCat 的「必须带 prompt_text」少一整条 ASR 前置链路。
- 参考音频时长要求：官方 README 未给硬性下限；`examples/voice_01.wav` 等示例可直接用。**确切时长下限未核实。**
- 情感与音色解耦：可单独给 `emo_audio_prompt` 控制情感而不动音色。

#### 3.1.4 许可证

见 §1.3。要点：阈值内可商用；分发需附 LICENSE；不得用于改进其他 AI 模型；PRC 法 / 上海仲裁。

#### 3.2.2 中文效果（一手，VoxCPM2 模型卡）

- seed-tts-eval **test-zh CER 0.97 / SIM 79.5**；test-en WER 1.84 / SIM 75.3；test-hard CER 8.13 / SIM 75.3。

- 48 kHz 原生输出 + 内置超分（接受 16kHz 参考音频直接输出 48kHz）。

#### 3.2.3 零样本复刻

两种模式（一手 README）：
- **Controllable Voice Cloning**：只需 `reference_wav_path`，**不需要转写**；可用括号式风格指令 `"(slightly faster, cheerful tone)..."` 调速/调情绪，同时保持音色。
- **Ultimate Cloning**：同时给参考音频 + 其转写文本，从参考处无缝续写，最大保真。**这个模式需要转写。**

#### 3.2.4 许可证

代码 + 权重均 **Apache-2.0**，官方 README 明写 *"Fully Open-Source & Commercial-Ready — Weights and code released under the Apache-2.0 license, **free for commercial use**"*。附带一段非许可性声明（禁止用于冒充/欺诈/虚假信息、建议标注 AI 生成）。**这是本表里许可证最干净的强中文候选。**

#### 3.2.5 安装

- `pip install voxcpm`（官方 README 原文）。
- 要求：**Python ≥3.10, <3.13；PyTorch ≥2.5.0；CUDA ≥12.0**。
- `pyproject.toml` 依赖（无 fairseq / deepspeed / flash-attn / pynini）：
  `torch>=2.5.0, torchaudio>=2.5.0, torchcodec, transformers>=4.36.2, einops, gradio>=6,<7, inflect, addict, wetext, modelscope>=1.22.0, datasets>=3,<4, huggingface-hub, pydantic, tqdm, simplejson, sortedcontainers, soundfile, librosa, matplotlib, funasr, spaces, argbind, safetensors`
- **Windows 风险点**：
  - `torchcodec`：**实测 PyPI 有 win_amd64 wheel**（cp310–cp314 共 63 个 win 文件）→ 可装。但 torchcodec 运行期需要 **FFmpeg 动态库**，这是系统级依赖 → **需随包分发 ffmpeg**（另见 MOSS-TTS 同样问题）。
  - `funasr`、`spaces`、`argbind`、`gradio>=6,<7`：非必需功能的重量级依赖（funasr 是 ASR，VoxCPM 用它做某种辅助），会显著拉长安装时间与体积。**是否可裁剪需实测（未核实）**。
  - `Development Status :: 3 - Alpha`。
  - 自述局限：*"Voice Design and Controllable Voice Cloning results **can vary between runs** — you may try to generate 1~3 times to obtain the desired voice or style."* → 音色设计功能的**结果不确定性**要在 UI 上体现（生成多次供挑选）。

#### 3.2.6 成熟度

GitHub **37,613** star（比 IndexTTS 高）、Apache-2.0、最后提交 **2026-09-02**、121 open issues。
生态：官方 Python API、CLI（`voxcpm` 入口）、Gradio Web Demo、**vLLM-Omni（PagedAttention + OpenAI 兼容 API）**、Nano-vLLM（`a710128/nanovllm-voxcpm`，308 star）、`bluryar/VoxCPM.cpp`（llama.cpp-omni 端侧）、GGUF 量化（多个第三方仓）、ReadTheDocs 文档。

#### 3.2.7 已知坑

- 音色设计 / 可控复刻**跨次运行结果不稳定**（官方自述，需重试 1–3 次）。
- `torchcodec` → **依赖系统 FFmpeg 动态库**（官方 Quick Start 要求 `apt-get install ffmpeg` / `brew install ffmpeg`；Windows 需自行放 dll）→ 必须随包分发。
- 权重 9.54 GB（比 IndexTTS 的 5.49 GB 大 74%）。
- 显存 ~8GB → **8GB 卡上会很紧张**（系统 + CUDA context 之后几乎没有余量）。
- ⚠️ **传递依赖把 CUDA torch 顶掉 → 静默退回 CPU 跑**（issue #60，2025-10-03，**closed**）：用户报告 `torch 2.8.0+cpu`、CUDA unavailable，怀疑 *"FunASR/ModelScope auto-installs CPU torch over GPU build"*，最终 **29s 音频跑 700s**（RTF ≈ 24，RTX 3060 6GB）。https://github.com/OpenBMB/VoxCPM/issues/60

  **这是 §0.5 描述的失败模式的原始现场。VoxCPM 依赖 `funasr`，因此风险比 IndexTTS 高。** 若选 VoxCPM2 作 v1，必须在安装后强制自检 `torch.cuda.is_available()`。
- ⚠️ **Windows 上 `_normalize_loudness` 运行时报错**（issue #315，2026-05-24，**open**，Windows + Torch 2.11.0+cu128 + RTX 5070 Ti）。https://github.com/OpenBMB/VoxCPM/issues/315 → 需版本组合锁定或打补丁。
- ⚠️ **Windows 上的隐藏重量级依赖**（issue #184 *"Many errors in Windows 11"*，2026-02-07，closed）：启动日志显示它会从 ModelScope 下载 **`iic/SenseVoiceSmall`（893 MB）** 这个 ASR 模型——即使用户只想做 TTS。https://github.com/OpenBMB/VoxCPM/issues/184
  → **实际首装体积 = 权重 9.54 GB + 辅助 ASR 模型 ~0.9 GB**，且离线环境会失败。必须预热。
- ⚠️ **Windows CUDA 安装器仍未内置**（issue #349 *"[codex] Add full Windows CUDA installer"*，2026-06-30，**open**）；以及 #151 *"Add comprehensive Windows setup guide"*（2026-01-20，closed）、#259 *"[Windows] No triton, no worries. Use flash attention 2."*（2026-04-13，open）。https://github.com/OpenBMB/VoxCPM/issues/349
  → 对照 §3.1.7：IndexTTS 的 Windows 适配是**官方做进 pyproject 的**，VoxCPM 的 Windows 支持更依赖**社区 issue/PR**。这是两者在「安装确定性」上的真实差距。
- 3090 相关数据点（**微调**，非推理）：issue #335（2026-06-08）称用 4×3090 24G（共 96G）做全参数微调仍 OOM，而官方称 40G 足够。https://github.com/OpenBMB/VoxCPM/issues/335 → **与我们的推理场景无关，不要引用为推理显存证据。**
- 并发 / 显存释放行为：**未核实**。

前提：Windows 11 桌面环境下，`torch` CUDA context 自身约占 **0.8–1.5 GB**；浏览器/桌面合成器另占 0.5–1.5 GB。以下为**规划建议**，非实测。

|---|---|---|---|---|
| **8 GB** | RTX 3060 Ti / 4060 / 2060S (8G) | **IndexTTS-2.5（bf16）** — 官方 6GB，是本档唯一有官方显存数字背书的强中文引擎。**必须关掉 QwenEmotion**（`use_qwen_emo=False`），`use_random=False`。 | **bf16**（可选组 `accel` 不要装 flash-attn；**`triton-windows` 可装**以启用 `torch.compile` 加速 s2mel） | ✅ **v1 主战场**。默认走 IndexTTS-2.5 + bf16 + 不装 deepspeed/flash-attn。**⚠️ 8GB 是本档最紧的配置，叠加 #630 的显存泄漏会更快触顶** → 进程级回收阈值要设得更激进（如每 10 次生成或 >6.5GB 就重启 worker） |

### 4.1 量化（int8 / GGUF / AWQ）现状

- **IndexTTS-2.5：官方未提供 int8/4bit 量化权重。** HF 上第三方有 `Richasy/IndexTTS-2.5-GGUF`、`xxliam/IndexTTS-2.5-GGUF`、`t8star/IndexTTS-2.5-Comfy`（均 `license:other`），**但第三方量化权重的许可证状态与数值保真度均未核实，不建议 v1 采用**。官方路径是 **bf16/fp16**（README 明说「半精度非常有益：推理更快、显存更低、质量损失极小」）。
- **VoxCPM2**：HF 上有第三方 GGUF（`DennisHuang648/VoxCPM2-GGUF`、`cstr/voxcpm2-GGUF`，均 apache-2.0，下载 9,121 / 4,284）与 MLX 量化（`mlx-community/VoxCPM2-bf16` / `-8bit` / `-4bit`）。**CUDA 侧的 GGUF 是否能在我们的 uv 运行时里直接用，未核实。** 官方 CUDA 路径是 PyTorch 全精度/半精度。
- **结论**：**v1 不做量化。** 靠 bf16 + 显存分档（IndexTTS-2.5 的 6GB）覆盖 8GB 档。量化作为 v1.1+ 的「12GB 卡跑 VoxCPM2」的备选手段再评估。

### 5.1 会在**依赖解析 / 安装阶段直接失败**（必须排除或改写依赖）

> **三条可操作的结论**：
> 1. **绝对不要在我们的安装路径里引入 `flash-attn`**——它在 PyPI 上没有任何 wheel，等于强制终端用户编译。
> 2. **Windows 上要 triton 就用 `triton-windows`**，不要直接依赖 `triton`。
> 3. **IndexTTS 的 `deepspeed==0.17.1` 在 Windows 上无 wheel**。我们的安装配方应**完全不装 deepspeed**（连 `--extra deepspeed` 都不用），把「官方说 DeepSpeed 可能更快也可能更慢，需自行开关测试」这条当作已知的、可在后续版本单独实验的优化项。

### 5.4 推荐的安装调用（可直接落地）

## 6. 「安装风险」之外的补充：产品级注意事项

1. **显存释放 + 进程级回收都是刚需**：issue #649 证明常驻会吃 10GB；**issue #630 进一步证明这是会持续累积的泄漏**（12GB → 16GB 只涨不落，*"Restarting the service frees up the memory"*，至 2026-09 仍 open）。所以封装层需要三层防护：
   - `unload()`：显式卸载模型；
   - 空闲超时释放（例如 5 分钟无请求）；
   - **进程级回收**：连续 N 次生成、或显存占用超过阈值时**重启 worker 进程**——这是唯一被证据支持的彻底解法（用户原文就是靠重启恢复的）。
   UI 要展示显存占用，让用户能看到问题。
2. **半精度必须是默认值**：issue #585 的 RTF 13.11 是「默认配置太慢」的反面教材。
3. **段落切分与韵律**：IndexTTS-2.5 官方承认长文分段后段间韵律不建模。产品侧应把「长文」拆成句/段并在 UI 上按段预览，而不是假装一次生成整篇。
4. **许可证合规的落地动作**（IndexTTS-2.5）：
   - 安装包内附 `LICENSE` + `LICENSE_ZH.txt` 副本（§3.4(b) 强制）；
   - 「关于」页标注模型来源 = bilibili IndexTeam IndexTTS-2.5、协议 = bilibili Model Use License、商用阈值；
   - 禁止把合成结果用于改进其他 AI 模型（§3.4(c)）——这条要写进内部规范，防止有人拿输出做蒸馏/微调；
   - 分发衍生权重时须附免责声明（§4.1(a)）；
   - 风险登记册记录「MAU 1 亿 / 营收 10 亿人民币」触发点。
5. **参考音频的授权**：IndexTTS-2.5 模型卡明确 *"The model does not verify that the speaker in a reference clip consented to being cloned. Obtaining that consent is the user's responsibility"* —— 产品必须自己做「本人授权」确认 UI（这也是国内深度合成法规的要求）。
6. **并发**：IndexTTS 的并发能力**未核实**；内嵌架构建议**单实例 + 串行队列**，一次只跑一个生成任务。

### 6.1 ⚠️ Windows 部署的三个具体陷阱（全部有一手 issue 佐证）

#### (a) 安装路径含**非 ASCII 字符**会打断 CUDA 内核 JIT 编译 —— 直接命中我们自己的项目路径

**IndexTTS issue #93**（2025-04-15，closed）原文：
> 「如果 index-tts 项目拉取在某些**中文路径**下，比如含中文目录：`j:/语音克隆/index-tts`，当启用 `use_cuda_kernel = True` 时，运行项目会生成 **build.ninja 中文乱码**，从而导致 **BigVGAN cuda kernel 编译失败**。经过检测发现 `cpp_extension.load` 以及后续代码均执行失败。」
> 失败日志：`Failed to load custom CUDA kernel for BigVGAN. Falling back to torch.`
> https://github.com/index-tts/index-tts/issues/93

**为什么我们必须当真**：
- 我们自己的仓库路径就是 `/Users/smallmj/My Projects/声音复刻软件` —— **同时含空格与中文**；
- Windows 用户更常见：`C:\Users\张三\...`、`D:\语音软件\...`、`C:\Program Files\...`（空格）。
- 根因是 **ninja + `cpp_extension.load` 对构建路径的编码处理**，属于 CUDA JIT 编译的**固有类别**问题，不是一次性 bug；这次的补丁修了 BigVGAN，别的算子/别的版本仍可能复发。

**对策（三条都要做）**：
1. **安装根目录强制 ASCII**：例如 `C:\ProgramData\VoiceClone\` 或 `%LOCALAPPDATA%\VoiceClone\`，绝不放在含中文/空格的路径下；
2. **把 PyTorch 扩展构建目录也指到 ASCII 路径**：设置 `TORCH_EXTENSIONS_DIR` 环境变量（例如 `C:\ProgramData\VoiceClone\torch_ext`）；
3. **在产品侧做成「可降级」而非「硬失败」**：`use_cuda_kernel` 失败应捕获并回落到纯 torch 路径（日志里官方就是这么回落的），同时**在 UI 上提示原因**，而不是给用户一个看不懂的编译错误。

#### (b) Windows 上 cuDNN 的动态库发现是高频摩擦点

**IndexTTS issue #782**（2026-08-18，**open**）标题：
> *"Could not locate **cudnn_engines_runtime_compiled64_9.dll**. Please make sure it is in your library path!"*
> 用户描述：*"its in my PATH in my system variables? `C:\Program Files\NVIDIA\CUDNN\v9.25\bin\13.4\arm64` ... I can run comfy perfectly but this voice Ai thing beating me up, **I had past issues with 2.0 too**"*
> https://github.com/index-tts/index-tts/issues/782

**读法**：该用户装的是 **arm64** 版 cuDNN（自己装错了架构），但真正的信号是：
- 这类 DLL-not-found 是 Windows 部署的**高频工单来源**；
- **IndexTTS 的 `pyproject.toml` 已经给了更省事的路子**：`accel` 可选组里显式列了 **`nvidia-cuda-runtime-cu12` + `nvidia-cudnn-cu12`** —— 即用 **pip 装的 NVIDIA 运行时 wheel**，自带 DLL，不依赖用户机器上的系统 CUDA Toolkit / cuDNN。
- 官方 README 又说「遇 CUDA 报错请装 CUDA Toolkit **12.8+**」——**两条路都能走通，但方向相反**。

**对策**：我们的安装器**优先走 pip 的 `nvidia-*` wheel**（自包含、可控、可复现），把「装系统 CUDA Toolkit」当作最后手段；并在启动前做一次 DLL 可加载自检。

#### (c) torch/torchaudio 版本漂移会导致**静默的音频数据损坏**

**IndexTTS issue #724**（2026-07-30，closed）标题：
> *"Audio save path is incompatible with **TorchAudio 2.9+** and can **silently saturate** generated WAV files"*
> 正文要点：IndexTTS 保存时先把波形转成 PCM 量级 `wav = torch.clamp(32767 * wav, -32767.0, 32767.0)`，再以 `int16` 传给 `torchaudio.save()`。**从 TorchAudio 2.9 起 `save()` 委托给 TorchCodec**，该路径把 PCM 量级的 `int16` **不做归一化**地转成 `float32`，再按 `[-1, 1]` 解释 → **保存不报错、不告警，但 WAV 被削顶饱和，幅度信息全毁**。官方依赖钉死 `torch/torchaudio == 2.8.*`，所以官方安装不受影响；**只有在升级/改造/下游打包环境中才暴露**。
> https://github.com/index-tts/index-tts/issues/724

**这对我们架构的直接约束**：
- 我们要在**每实例 venv** 里同时/先后装多个引擎；**绝不能为了兼容别的引擎而升级某个引擎 venv 里的 torch/torchaudio**。必须**逐引擎钉版本、venv 完全隔离**。
- 需要一条**输出数值自检**作为 smoke test：合成后检查音频峰值/是否接近满量程削顶，防止这类「静默损坏」被当成质量差或模型问题去排查。

## 10. 给决策者的一页纸

| 问题 | 答案 |
|---|---|
| **v1 用哪个** | **IndexTTS-2.5**（bilibili IndexTeam） |
| 为什么 | 唯一把「uv + Windows CUDA」当一等需求的候选：`uv.lock`、win32 依赖分支、官方 Windows/deepspeed 说明、`gpu_check.py`；基础依赖零编译；~6GB 显存（8GB 卡可跑）；中文 CER 1.03/SIM 76.5（2.0 口径）+ 拼音多音字显式控制；CLI 带结构化退出码，内嵌封装成本最低 |
| **v1.1 效果档** | **VoxCPM2**（Apache-2.0，CER 0.97/SIM 79.5，音色设计，48kHz，~8GB） |
| 8GB 卡 | IndexTTS-2.5 bf16，关 QwenEmotion；不装 deepspeed/flash-attn；可装 triton-windows |
| 12GB 卡 | IndexTTS-2.5 全开 + VoxCPM2 |
| 24GB（3090） | 双引擎常驻；开 `torch.compile` + `triton-windows`；**deepspeed 不要用 0.17.1**（Windows 无 wheel，只到 0.16.5），确要实验就钉 0.16.5；考虑 TensorRT / vLLM（均未声明 Windows）；**必须配进程级回收** |
| 量化 | **v1 不做**。官方无 int8/4bit 权重，仅 bf16/fp16 |
| 会炸的候选 | **MegaTTS3 / dots.tts**（`WeTextProcessing`→`pynini` 无 Windows wheel，解析期失败）；**GPT-SoVITS**（opencc 强制源码编译 + pyopenjtalk/jieba_fast 无 wheel） |
| 三条禁令 | ① **永不引入 `flash-attn`**（PyPI 上连一个 wheel 都没有，等于让用户现场编译）；② `triton` 在 Windows 上一律换 `triton-windows`；③ **不装 `deepspeed`**（IndexTTS 钉的 0.17.1 在 Windows 上无 wheel，官方也因此建议去掉 `--all-extras`） |
| ⚠️ 最大的隐性杀手 | **传递依赖把 CUDA torch 顶成 CPU torch**（VoxCPM #60 实测：装好了 GPU 版却 `torch 2.8.0+cpu`，29s 音频跑 700s）。对策：torch/torchaudio 写成**直接依赖** + `[[tool.uv.index]] explicit = true`（**照抄 IndexTTS 的 `[tool.uv.sources]`**）+ **安装后断言 `torch.cuda.is_available()` 否则拒绝启动** |
| 三条必做 | ① 默认开半精度；② 模型卸载**+ 进程级回收**（IndexTTS #630 有至 2026-09 未修的显存泄漏）；③ 安装路径显式列 extras，**禁用 `--all-extras`** |
| ⚠️ 最容易被忽略的坑 | **安装路径不能含中文/空格**（IndexTTS #93：中文路径 → `build.ninja` 乱码 → BigVGAN CUDA 内核编译失败）。我们自己的路径 `My Projects/声音复刻软件` 就中招 → 安装根目录强制 ASCII + 设 `TORCH_EXTENSIONS_DIR` |
| 版本漂移风险 | **torch/torchaudio 必须逐引擎钉版本、venv 完全隔离**（IndexTTS #724：TorchAudio 2.9+ 起 `save()` 走 TorchCodec，会把 WAV **静默削顶饱和**，不报错不告警）；并加输出峰值自检 |
| 最需要补的实测 | 在真机 RTX 3090 上测 IndexTTS-2.5 与 VoxCPM2 的 **RTF 与峰值显存**（目前全部为 4090 数据或推算） |
